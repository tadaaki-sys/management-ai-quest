# 管理職AIクエスト ― 失われた時間を取り戻せ

3分間の「業務改善クエスト」を通じて、管理職が自分の時間をどこで失っているか、AIに任せられる工程はどこか、自分自身が判断すべき工程はどこかを可視化する、ゲーム型のAI業務削減診断Webアプリです。

**外部API・生成AI APIは一切使用していません。** すべての診断結果は、回答内容から静的なロジックで算出されます。データは端末の `localStorage` にのみ保存され、外部送信は行いません。

---

## 1. コンセプト

> AIに仕事を奪わせるのではなく、AIに「作業」を任せて、管理職が「判断」に集中できる時間を取り戻す。

「診断」ではなく、**管理職の時間を喰らう魔物「タイムイーター」を討伐していく3分間のクエスト** として設計しています。ただしゲーム演出は目的ではなく手段です。業務改善ツール80% × ゲーム20%を目安に、UIの信頼感（SmartHR / freee / Notion / Microsoft 365 的なトーン）をベースに、RPG的要素（ミッション、ゲージ、スコア、レベル、リザルト）を20〜30%だけ加えています。

## 2. ペルソナ

**山田さん（仮）／44歳／従業員300名規模企業の課長／部下8名**

- プレイヤー業務と管理職業務を兼務。定時までは顧客対応・社内問い合わせ・部下対応・会議で埋まり、定時後にようやく自分の仕事に着手できる。
- 週報取りまとめと会議資料作成だけで毎週数時間を消費している。
- ChatGPTに週報を貼って「要約して」と頼んだ経験はあるが、当たり障りのない要約しか返らず結局書き直した。「うちの仕事は文脈が多すぎてAIには無理では」と感じている。

このアプリは山田さんに対して「全部AIに任せる必要はない。この工程まではAI、ここから先はあなたの仕事」と、工程単位で具体的に示すことを目的としています。

## 3. ゲーム設計（体験フロー）

```
START
 → MANAGER STATUS（???表示、これから判明する演出）
 → MISSION 1：討伐するタイムイーター（業務）を選択
 → MISSION 2：共通診断（3問）
 → 選択した業務ごとのミッション（重点：週報・会議資料）
 → ANALYZING（QUEST COMPLETE 演出、即時解析）
 → RESULT（削減時間・優先順位・工程分解・プロンプト獲得）
```

### 挿絵とキャラクター

RPG調の描き下ろし挿絵を使用しています。

| 素材 | 使用箇所 |
|---|---|
| メインビジュアル（勇者と城） | START画面／OGP画像 |
| タイムイーター（敵キャラ） | STATUS画面の敵紹介、BOSS BATTLEのボス立ち絵 |
| 5業務エンブレム | MISSION 1の業務カード（外周を透過処理） |
| クエストクリア | RESULT画面の最上部 |

クエストクリアの挿絵は、元画像に焼き込まれていた「+2時間」「S」「ゲージ」を書き出し時に背景色で塗り潰し、**実際の診断結果をHTMLで重ねて表示**しています。値の位置は画像に対する％指定、文字サイズはコンテナ相対単位（`cqi`）なので、画面幅が変わってもスロット内に収まります。

- 時間回復量：週あたりの削減時間（例 `+4時間4分`）
- 総合評価：TIME RECOVERY SCORE を S/A/B/C/D に変換（S:80以上／A:65／B:50／C:35／D:35未満）
- ゲージ：スコアと同じ割合で伸びる

敵は架空のモンスターではなく、**実在する業務そのもの**です。これを「タイムイーター（時間を喰らう魔物）」と総称し、業務カードとして提示します（例：週報 = WEEKLY REPORT、会議資料 = MEETING MAKER）。呼称と動詞（討伐・撃破・BOSS）でクエストらしさを出しつつ、カードの中身は実際の業務名・頻度・削減時間のままにすることで、業務リアリティを損なわない設計にしています。

### 業務の重み付け（意図的な非均等設計）

開発時間（3〜5時間相当）を踏まえ、全業務を均等に作り込むのではなく、ペルソナの負荷が大きい業務を重点設計しています。

| ランク | 業務 | 設問数 |
|---|---|---|
| S | 週報・日報取りまとめ | 4問（部下人数／確認時間／工程／フォーマット統一度） |
| A | 会議資料・議題作成 | 3問（作成時間／工程／前回との類似度） |
| B | 評価コメント | 1問 |
| B | 稟議・申請書 | 2問 |
| B | 部門数字説明 | 1問 |

共通設問3問と合わせ、選択数に応じて総設問数は概ね5〜14問（3分以内）に収まるよう設計しています。

## 4. 設問設計のポイント

- 1画面1問。進捗バーと `Question X / N` 表示で残量を明示。
- 選択していない業務の設問は一切表示しない（分岐制御）。
- 重要な回答（AI活用度・週報フォーマット・会議資料の類似度）には、選択直後に短いミニフィードバック（「AI適性 +12／定型業務はAIとの相性が高いです」等）を表示し、回答の意味づけを即座に返す。
- 画面上部の `LOST TIME` ゲージは診断中は推定値で更新され、結果画面では `RECOVERED TIME` として意味が反転する。

## 5. 計算ロジック

乱数は一切使用していません。すべて回答から決定的に算出します。

### 5.1 基本式

```
削減可能時間 = 現在時間 × AI工程適用率 × 実行容易性補正 × 判断必要度補正
```

業務全体に一律の削減率をかけるのではなく、**工程（ステップ）単位** で分解して計算しています（`script.js` の `buildXxxSteps` 関数群）。

### 5.2 グローバル補正（`globalFactors`）

- **実行容易性補正**：生成AI活用度（0〜4）から `0.88〜1.12` の係数を算出。活用度が高いほど、理論上の削減がそのまま実現しやすい。
- **判断必要度補正**：「自分で最終判断する必要がある業務割合」（5%〜95%）から `0.665〜0.9825` の係数を算出。判断比率が高いほど削減余地は小さくなる。

### 5.3 工程別AI適用率（例：週報取りまとめ）

| 工程 | 適用率 | 分類 |
|---|---|---|
| 読む（人数×確認時間） | 45% | AI |
| 重要事項の抽出 | 75% | AI |
| 問題案件の発見 | 55% | AIと一緒に |
| 全体整理 | 75% | AI |
| 上司向け報告文の作成 | 65% | AIと一緒に |
| 会議資料への転記 | 80% | AI |
| 部下へのコメント返信 | 50% | AIと一緒に |
| 最終判断（常時発生・選択不可） | 10% | あなたがやる |

会議資料・評価コメント・稟議・部門数字説明についても同様に工程分解し、それぞれの工程に適用率とカテゴリ（AI／AIと一緒に／あなたがやる）を付与しています。

### 5.4 削減率の上限

`applyGlobal()` にて、1工程あたりの削減は最大72%（元の時間の28%は必ず残る）にクランプ。判断系の工程はそもそも適用率が10〜15%に設定されているため、非現実的な削減（管理職の判断そのものをゼロにする）が起きない設計です。

### 5.5 AI TRANSFORMATION RANKING（優先順位スコア）

```
Priority = 削減時間(50点) + 定型性(25点) + 実行容易性(25点)
```

削減時間は選択業務内での相対値（最大削減業務を50点満点として正規化）、定型性は工程の加重平均AI適用率、実行容易性はグローバルな実行容易性補正から算出します。

### 5.6 AI LEVEL / TIME RECOVERY SCORE

- **AI LEVEL（1〜5）**：AI活用度・平均定型性・判断比率から算出。レベルが低くても否定的な表現は使わず、「AI未開拓マネージャー」等、伸びしろとして表現。
- **TIME RECOVERY SCORE（0〜100）**：削減時間・定型性・AI未活用余地・実行容易性を加重合算。

### 5.7 称号（Achievement）

週あたり削減時間に応じて4段階（改善の第一歩／時間回収マネージャー／AI委任マネージャー／TIME ARCHITECT）。評価目的ではなく遊び心として使用。

### 5.8 Confetti演出

`canvas-confetti` は週90分以上の削減が算出された場合のみ、結果表示時に1回だけ控えめに発火します。

## 6. AI / HUMAN の境界線

全工程を3分類し、結果画面に3カードで表示します。

- **AIに任せる（HIGH）**：要約・分類・転記・下書き
- **AIと一緒に（MEDIUM）**：問題候補・コメント案・原因仮説
- **あなたがやる（LOW）**：優先順位・意思決定・部下への指示・承認

さらに `DO NOT AUTOMATE` セクションで、削ってはいけない「判断」工程の時間を明示し、「AI化の目的は判断をなくすことではなく、判断以外の作業を減らすこと」というメッセージを添えています。

## 7. 動的AIプロンプト生成

固定文言のコピペではなく、診断内で得た回答（部下人数、フォーマット統一度、選択した工程、前回資料との類似度など）を `script.js` の `genWeeklyPrompt` / `genMeetingPrompt` / `genEvalPrompt` / `genRingiPrompt` / `genReportPrompt` がテンプレートに反映して生成します。

いずれのプロンプトも共通して、AIには「判断」ではなく「判断前の情報整理」だけを担当させる設計になっており、事実と推測の分離・情報不足の明示・最終判断の留保をルールとして明記しています。結果画面では、AI変革ランキング1位の業務に対応するプロンプトを `NEW TOOL UNLOCKED` として提示します。

## 9. 試行錯誤ログ（DESIGN ITERATION LOG）

**Iteration 01**
- 初期：普通の診断フォーム
- 問題：既視感が強く、3分間触り続ける動機が弱い
- 改善：MISSION形式（QUEST START / MISSION 1 / MISSION 2 / RESULT）へ変更
- 理由：3分間の回答体験を「クエストの進行」として維持するため

**Iteration 02**
- 初期：削減時間だけを表示
- 問題：根拠が示されず、山田さんのような慎重な管理職には信用されない
- 改善：現在時間とAI導入後時間を工程単位で併記し、「削減時間の根拠」セクションを追加

**Iteration 03**
- 初期：AI化できる工程のみを表示
- 問題：「本当に全部AIに任せていいのか」という不安が残る
- 改善：`DO NOT AUTOMATE`（削ってはいけない時間）を追加し、判断工程を明示的に保護

**Iteration 04**
- 初期：週報要約用の固定プロンプトを表示するだけ
- 問題：診断で答えた内容（部下人数・フォーマット・工程）とプロンプトが連動しておらず、「結局当たり障りのない指示」になってしまう
- 改善：JavaScriptで回答内容をプロンプトのシステム設計・作業手順・追加タスクに反映する動的生成に変更

**Iteration 05**
- 初期：5業務すべてを均等な設問数・演出量で設計
- 問題：開発時間内では全業務を厚くできず、結果として全体が薄くなる
- 改善：週報（Sランク）・会議資料（Aランク）を重点設計し、残り3業務は1〜2問の軽量診断に整理

**Iteration 06**
- 初期：削減率を業務全体に一律60%などで適用
- 問題：どの工程が削減対象か曖昧で、「本当にこの数字は正しいのか」という説得力に欠ける
- 改善：工程（ステップ）ごとにAI適用率を個別設定し、`最終判断`などの人間工程には低い適用率（10〜15%）を固定で持たせる設計に変更

| ケース | 内容 | 確認結果 |
|---|---|---|

| B | 会議資料のみ選択 | 共通3問＋会議3問の計6問で完走できることを確認 |
| C | 5業務すべて選択 | 共通3問＋業務別11問の計14問、3分程度で完走できることを確認 |
| D | 部下8名／1人8分／フォーマット統一 | 読む工程 64分、取りまとめ工程との合算が現在時間に正しく反映されることを確認 |
| E | AI活用「ほぼ毎日」 | 実行容易性補正が最大（1.12）になり、削減率が上振れすることを確認 |

## 11. GitHub Pagesでの公開方法

1. このディレクトリ（`index.html` / `style.css` / `script.js` / `README.md`）をGitHubリポジトリの直下（またはルートとして指定するフォルダ）にpushします。

```bash
git init
git add index.html style.css script.js README.md
git commit -m "Initial commit: 管理職AIクエスト"
git branch -M main
git remote add origin <あなたのリポジトリURL>
git push -u origin main
```

2. GitHubリポジトリの **Settings → Pages** を開きます。
3. **Source** を `Deploy from a branch` に設定し、Branch を `main` / フォルダを `/ (root)` に指定して **Save** します。
4. 数分後、`https://<ユーザー名>.github.io/<リポジトリ名>/` で公開されます。

外部APIを使用していないため、追加のシークレット設定や環境変数は不要です。
